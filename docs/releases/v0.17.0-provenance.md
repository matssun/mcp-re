## Measured on the approved candidate, and why it carries

**The ADR-MCPRE-051 §7 local SLO lane** was measured on `b7977957`: **PASS 6/6 reps**,
median **15,282.6 rps** against the committed anchor's 15,454.9 — **98.9%** retained — with
p50 7,811–8,153 µs and every rep inside the p99 and p999 ceilings.

It is recorded against the candidate rather than the frozen SHA because that is the tree the
binary was built from, and the frozen SHA's tree is the same object. The delta is not
"documentation only", as v0.16.0 had to argue: it is **nil**.

A repeat on the frozen SHA was attempted and **not** taken: the machine did not return to
the lane's quiet threshold (1-min load ≤ 4.2 on 14 cores) while unrelated builds were
running on it, and the lane is right to refuse to measure there. Re-running it would have
produced a second reading of the same bytes under worse conditions, which is not better
evidence — and `ALLOW_NOISY_BOX=1` is not an option this project takes.

**No production SLO threshold is declared by this run.** The v0.16 position is unchanged:
the GKE release-build figures remain the accepted ones, the old production SLO declaration
remains `invalidated-pending-remeasurement`, and this is a local-regression measurement
against the committed local anchor.

## Infrastructure failures, reported as infrastructure failures

#836 requires that a required proof which did not run is not a PASS, and that environmental
failure is named as such. Three occurred, none of them a code result:

1. **The SLO bench could not start its Redis fleet** — `Can't open or create append-only dir
   appendonlydir: No space left on device` inside the Docker VM. The lane reported
   `FAIL — the run did not execute exactly one bench test. (0 passed … nothing was
   measured.)`, which is the refusal it exists for. Reclaimed 21.6 GB of Docker build cache
   and dangling images, then measured.
2. **Two INCONCLUSIVE SLO rounds under host contention** — the load generator is co-located
   with the proxy and unrelated builds were running on the same machine. The lane says so in
   its own words and refuses to let contention read as a regression. The recorded figures are
   from the quiet-box round.
3. **Proof 4's load generator was OOM-killed** on the first frozen-SHA attempt — `command
   terminated with exit code 137`, in an 8.3 GB Docker VM shared with unrelated containers.
   The harness reported `PROOF FAILED: load generator did not complete (no summary; exec
   killed?) — cannot confirm zero-drop` rather than passing on a missing summary. The retry
   completed 1,745 requests with 0 drops.

### The stage-4 obligation, and the owner ruling that settled it

`scripts/local_gate.sh` stages 1, 2, 3 and 5 were re-run on `c1365e22` on 2026-09-08 and
were **green** — `VERIFICATION: PASS` with 111 units, 126/126 theorems established, 12/12
roots complete, bazel 58/58, and ALL EIGHT LIVE PROOFS PASSED on a rebuilt three-replica
kind fleet.

Stage 4 was **not** re-measured on `c1365e22`, under the **owner ruling of 2026-09-08**:

> a minor release does not require a whole SLO run; that belongs where code plausibly
> affecting performance was touched. What a release does require is that everything
> compiles and every test is green.

The ruling is sound on this release's own evidence. The ADR-MCPRE-051 §7 obligation was
already discharged for these exact bytes: tree object `d8a53be9…` measured **6/6 PASS,
median 15,282.6 rps, 98.9% of the committed anchor**, on a quiet box. A re-run on 2026-09-08
returned 4/6 FAIL — and it was the box, provably: rep 2 reported p99 **262,944 µs** and max
**445,764 µs**, which is descheduling rather than serving, while **48,000/48,000** requests
succeeded across both rounds. Byte-identical inputs cannot regress. `ALLOW_NOISY_BOX` was
never set.

**Recorded as a v0.18 obligation rather than closed here:** the SLO lane is the only
evidence in this repository that is not content-addressed. `.verification/attestations` are
keyed on a fingerprint and are never re-derived while inputs are unchanged; the SLO lane
re-measures unconditionally, which is why an unchanged tree was asked to prove itself twice.
Keying an SLO result on (tree, toolchain, hardware_class) and moving the lane to the
self-hosted dev1 runner is the fix, and it is the shape the owner directed.

### One protocol defect found by following the protocol

`docs/security/eks-slo-baseline-runbook.md` states that local-gate stage 5 "additionally
rehearses the **exact** SLO Job spec this runbook schedules". **It does not.**
`tools/slo/run_slo_job.sh` is invoked by neither `scripts/local_gate.sh` nor
`docs/security/gke-multi-replica-validation.sh` — grepped, zero hits. The rehearsal was
therefore run explicitly here, and it passed on the second attempt: Job spec, three native
Redis sidecars, bench image and marker-based report extraction, **8000/8000**. Its 7,448.7
rps is a plumbing number and was not fed to `scripts/slo_gate.py`.

The first attempt failed, and its cause is worth recording because it recurred: the Docker
VM disk was **98 GB, 100% full, 0 available**, so the Redis sidecars could not create their
append-only directories. The same condition had already killed the SLO bench's Redis fleet
the previous day. It is an environment fact, not a code result, and both lanes reported it
as one rather than passing.

This is the "configured is not alive" class the assurance platform exists to catch, in the
prose layer rather than the code layer. Recorded as a **v0.18** item; a freeze is not where
a runbook's wiring gets changed.

## What v0.17.0 does NOT claim

- **No GKE round was run for v0.17.** The eight live proofs were re-proven on a real
  three-replica Kubernetes fleet on `kind` — the identical harness, chart and images, only
  the cluster substrate differs. The v0.16.0 GKE round stands as the cloud evidence and is
  not restated as a v0.17 measurement.
- **The supply-chain claim is the Rust graph.** `cargo deny` reads Cargo manifests; it
  cannot see `sdk/python/uv.lock` (PyPI) or any `package-lock.json` (npm). Neither SDK ships
  a runtime dependency graph — the Python SDK declares no hard runtime dependencies and `mcp`
  is optional; the TypeScript SDK has no ordinary runtime dependency set and its MCP
  integrations are optional peer dependencies — so the absence of a PyPI/npm advisory lane
  does not block the v0.17 runtime dependency claim. A lane over those two graphs is future
  assurance-platform work, not a v0.17 gate. Owner ruling of 2026-09-07,
  [`verification/reviews/rulings/thm-0076-dependency-closure-2026-09-07.md`](../../verification/reviews/rulings/thm-0076-dependency-closure-2026-09-07.md) §4.
- **The images do not exist at the new tag** until
  `gcloud builds submit --config deploy/cloudbuild/mcp-re-images.yaml .` has run, and no
  local gate can tell you otherwise.
