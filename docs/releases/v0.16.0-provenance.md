## Two merge commits, one body of content

`main` carries two merge commits for one body of work:

| commit | merged | note |
|---|---|---|
| `c7f09413838cbdbb28e137b2d164c4c94c9da513` | PR #810 | 19:22:32Z |
| `f4cc65395f5b49a720cee36e68cea0900394042b` | PR #811 | 19:41:08Z |

The release plan was that **#811 supersedes #810 and contains it**, so #810 was not to be
merged separately. It was merged anyway, nineteen minutes before #811.

**Content effect: none.** #810's head `6f64db74` was already an ancestor of #811, so its
merge advanced `main` through commits #811 also carried. The released tree was verified
byte-for-byte against the approved candidate:

```text
main tree      1ff6fc6cca4e724c825aa86a239efafcef7d2858
0df482eb tree  1ff6fc6cca4e724c825aa86a239efafcef7d2858   IDENTICAL
```

`main` was deliberately **not** rewritten, reverted or force-pushed to remove the extra
merge commit: the artifact is history, the tree is correct, and rewriting a published
`main` to tidy provenance would trade a real risk for a cosmetic gain. Recorded here
rather than erased, and deliberately **not** described in the public release notes,
because it was not a product change.

## Evidence carried forward

The performance evidence was measured on the **measured runtime candidate** `dfd1e8c1`,
not on the released tree. That is legitimate because the delta between them was
established mechanically as documentation, benchmark metadata and test/benchmark targets
only — no production `src/`, no Cargo manifests or lockfile, no `deploy/` or `config/`, no
`VERSION` or toolchain, and no change to admission, signing, replay or KMS/Workload-Identity
behaviour. `deploy/docker/Dockerfile` builds `--bin mcp-re-proxy --locked` and never
compiles `tests/` or `examples/`, so the shipped binary's inputs are identical.

Performance rounds, accepted figures and every invalidated round:
[`../bench/v016-performance-rounds.md`](../bench/v016-performance-rounds.md).

Three facts kept distinct in the release record:

1. the v0.16 GKE release-build performance measurements are **accepted**;
2. the previous production SLO declaration remains **invalidated-pending-remeasurement**;
3. **no new production SLO threshold set was declared** by this campaign.

## Known gaps at release

- **`main` has no branch protection**, so no status check is actually *required* by GitHub
  (`GET /branches/main/protection` → 404). Every release gate is enforced by inspection.
  `scripts/merge_path_gate.py` cannot see this — branch protection is repository
  configuration, not tree content — and its own documentation says so.
- **A GKE cluster from the performance campaign is stranded.** Four Compute Engine zonal
  operations stalled at progress 0 from 2026-09-04T13:23Z, leaving two nodes wedged in
  `STOPPING` and the cluster undeletable through both CLI and console. Reported to Google;
  outside this project's authority and not a release blocker.
