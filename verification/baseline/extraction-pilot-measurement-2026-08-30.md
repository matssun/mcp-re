# Extraction pilot — first measurement of the pinned pipeline (MCPRE-130 / #541)

Measured 2026-08-30 against the pinned extraction container
`ghcr.io/matssun/mcp-re-verification-extraction@sha256:42318bba…7dce`, on the approved
target `mcp-re-core/src/time/format.rs`.

**Nothing here is evidence for any theorem.** No `lean://` URI is declared, no unit is V2,
and `verify-lean` still reports `NOT_REQUIRED`. This is the measurement #541's done
criteria require in their own right — *"measured tool limitations written down as such"* —
recorded before a proposition is chosen, so the proposition follows what the toolchain
actually supports rather than what would be convenient.

---

## 1. The pipeline runs on production Rust

Charon and Aeneas both execute, on the real crate, at the pinned commits:

```sh
charon cargo --preset=aeneas \
    --start-from "mcp_re_core::time::format::unix_to_rfc3339_utc" \
    --dest-file out.llbc          # 780,848 bytes
aeneas -backend lean -dest lean/ out.llbc
```

Two facts worth recording because neither is in any document:

* **`--preset=aeneas` is mandatory.** Without it Aeneas refuses the LLBC outright:
  *"the serialized crate was generated by Charon without the `--preset=aeneas` option."*
  A `regenerate-lean` that omits it produces a 780 KB artifact and no model.
* **`--start-from` is what keeps the extraction small.** Starting from the whole crate
  would drag in `ed25519-dalek`, `sha2` and `serde`. Pointing it at one item extracts two
  transparent functions and eight opaque ones.

`mcp-re-core`'s purity (ADR-MCPS-011/012) is what makes this work: no async, no I/O, no
FFI. It is the only crate in the workspace plausibly inside the supported subset, and the
reconciliation's reasoning for picking it survives contact with the tool.

## 2. What extracted, and what it costs — the finding that decides the theorem

`civil_from_days` extracts **fully transparent**: every one of its ~20 `i64` operations
appears in the model, inside Aeneas' `Result` monad where each `←` may `fail`. Both
`i64 → u32` casts appear as `lift (IScalar.hcast .U32 …)`, which also fails out of range.

`unix_to_rfc3339_utc` extracts, but its formatting half becomes **four axioms**:

| axiom | what it stands for |
|---|---|
| `core.num.I64.div_euclid` | the caller-domain bound `civil_from_days` depends on |
| `core.num.I64.rem_euclid` | the seconds-of-day bound |
| `alloc.fmt.format` | **the entire string production** |
| `core.hint.must_use` | the `#[must_use]` wrapper |

`alloc.fmt.format : core.fmt.Arguments → Result String` is uninterpreted. In the extracted
model the formatter's output is an arbitrary `String`.

> **Therefore the round-trip conjunct is not provable, and must not be promised.**
> *"formatting produces a canonical UTC RFC3339 value whose parse denotes the original
> instant"* quantifies over bytes the model does not constrain at all. Attaching it to a
> `lean://` URI would register a claim whose evidence establishes nothing about it.

What the model *does* support is the weaker, still-meaningful production proposition:

> For every `i64` in `civil_from_days`'s caller-supplied domain, the extracted model
> evaluates to `ok` — every intermediate `i64` operation is in range and both narrowing
> casts succeed.

That is worth having rather than a consolation prize. It is exactly the claim
`format.rs` currently asserts **in prose**, under a
`#[allow(clippy::arithmetic_side_effects)]` whose justification is an argument about the
argument's provenance plus two `i64`-extreme unit tests. Turning that argument into a
machine-checked one closes a documented class-C gap, and it is a direction THM-0002
explicitly scopes out — so it is a NEW proposition, never Lean evidence bolted onto
THM-0002's parsing totality.

Two model-boundary facts would have to become `ASM-NNNN` records with
`tool_specific_mechanism = "lean:…"`, not silent axioms:

1. `core.num.I64.div_euclid` / `rem_euclid` — the link from *any* `i64` to
   `civil_from_days`'s domain runs through them, so either they get a handwritten
   `models/` definition (TCB, registered) or the theorem stays conditional on the domain
   and the provenance link is the assumption.
2. `alloc.fmt.format` — permanently outside, and the reason to keep the formatting
   direction OUT of the proved statement rather than inside it as an assumption.

## 3. The blocker: the pinned image cannot run the Lean half

Steps 1–4 of the pipeline work. Steps 5–6 (lake build, `#print axioms`) cannot run in the
pinned image as built:

* `/root/.elan/toolchains` holds only `leanprover--lean4---v4.33.0`. The pin is
  **v4.31.0** — the toolchain the Aeneas Lean backend declares. The Dockerfile installs
  elan and notes that it *"resolves the exact toolchain from verification/lean/lean-toolchain
  at run time"*, so the pinned Lean is downloaded per run, not baked in.
* `/opt/aeneas/backends/lean/.lake` does not exist: the backend is **unbuilt**, and its
  `lakefile.lean` requires mathlib at `v4.31.0`. Neither mathlib's source nor its build
  cache is in the image.

So the Lean half currently means, on every CI run: download a Lean toolchain, fetch
mathlib, and build or cache-fetch both. That is a property of the image, not of the pilot,
and it has two consequences:

* **`verification/lean/lakefile.toml` cannot be authored against a Lean that has never
  run here.** Writing one now would be a pin to an unexercised environment — the failure
  mode `verification/lean/README.md` describes for an empty `lean-toolchain`.
* **Completing #541 requires a new extraction-image digest** carrying the pinned Lean
  toolchain and a built Aeneas backend. That is a toolchain-pin change plus a GHCR
  publish (`tools/verification/extraction-image`), which is an outward-facing action and
  an operator decision, not something to slip into a pilot branch.

The local attempt to work around it by building the backend inside the running container
ended in `No space left on device` — the Docker VM is full. That is an environment fact
about one workstation and is recorded only so the next attempt does not repeat it; the
image finding above is independent of it.

## 4. What #541 still needs, in order

1. **An extraction image that can run Lean** — pinned toolchain installed, Aeneas backend
   built, mathlib cached. New digest in `[extraction_container]`. *Operator action.*
2. `verification/lean/lakefile.toml`, authored against that image and exercised in it.
3. `regenerate-lean`: the invocation measured in §1, with `--preset=aeneas`, the
   `--start-from` set derived from the manifest, and each tool's exit status checked
   directly rather than through a pipeline.
4. The theorem from §2 — the totality direction, not the round trip — with the two
   model-boundary assumptions registered.
5. `verify-lean`: lake build, `#print axioms` discovery (never grep), `sorry` fail-closed
   with a negative control, and the stale / missing / zero-selection controls.

Steps 2–5 are ordinary work. Step 1 is the gate, and it is the reason this document exists
instead of a `lean://` URI.
