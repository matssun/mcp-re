## 1. The claim as it now stands

### Title — unchanged

The shipped Python SDK accepts only an answer to its own request

### Statement

> For the shipped Python SDK, an application is not handed, as this call's answer, a response
> from another exchange or signer, or one that verified only unbound — and is not led to
> repeat a side effect by reading silence as *it did not run*.
>
> Every reply is taken from the correlation entry the request created, and a reply binding to
> nothing outstanding, arriving late, or repeating one already answered is refused rather than
> delivered. A response is accepted only under the configured trust anchor, epoch, audience and
> revocation posture, measured against a RECORDED delegated session rather than a constructed
> one. A notification is delivered only against a signed acknowledgement. An elicitation pauses
> a call rather than ending it, so a reply that is not terminal — including one whose result
> type this SDK does not recognise — is refused rather than surfacing as the call's answer.
> A verified reply that is not an answer to this request — one carrying a method, or one with
> neither result nor error — is refused rather than dispatched.
>
> What the application is told about execution is what the receipt said, and nothing else. A
> verified receipt carrying execution and retry fields is reported with exactly those fields;
> a member the receipt did not carry is not invented for it. A LOCAL failure — a transport
> deadline, a cancellation, a local I/O or signing failure — is reported as a local and
> ambiguous failure under the SDK's own prefix: never as `not_executed`, never as retry-safe,
> and never as a wire code the peer did not send.

The final paragraph is the amendment. Its shape is the ruled one:

```text
verified receipt with execution/retry fields → report exactly those fields
verified receipt without a member           → do not invent that member
local timeout / cancellation / I/O failure  → local, ambiguous
                                            → NOT not_executed
                                            → NOT retry-safe
                                            → NOT a peer wire code
```

"The SDK reports NOTHING for such an exchange" is gone. A hang is not a security product,
and the durable proposition is the one above.

### Security consequence

> An application driving MCP through this SDK cannot be handed another exchange's answer, an
> answer from a signer this deployment does not trust, or a refusal that verified only unbound
> — and cannot be told that an operation did not run when the SDK does not know that.
>
> The last is the one a byte-level fixture cannot reach, and the timeout is where it bites: a
> response deadline is the condition under which this SDK knows LEAST about whether the call
> ran, so a synthesized `not_executed` or retry-safe verdict there is exactly what makes a
> caller repeat a tool call that already executed. Parity fixtures pin what this SDK EMITS;
> whether it invents an execution fact for a receipt that stated nothing is behaviour, and the
> two SDKs have diverged there before.

### Scope

Four paragraphs. The family boundary and the concurrency/throughput exclusion are unchanged.
Two are new or rewritten:

> THE RESPONSE DEADLINE IS ENFORCED, AND ITS WORST CASE IS STATED. The body is taken one
> underlying read at a time, so a peer that keeps sending returns control to the deadline
> after every read and cannot extend the response read at all; a peer that stops sending is
> ended by the per-recv bound the same `timeout` sets. The two compose into a real cap with
> a stated worst case — the deadline plus at most one per-recv stall — and it is measured
> against a real `http.client.HTTPResponse` fed by a real socket, both while trickling and
> while silent, never against a fake with short-read semantics the production reader lacks.
> What this claim takes from the bound is not availability but honesty: the deadline fails
> the exchange as a LOCAL condition, and no execution or retry fact is manufactured for it.

> WHAT A CALLER DOES NEXT IS OUTSIDE THIS ROOT. This claim says nothing about an application's
> own retry policy, its outer timeouts, or what it concludes from a local failure; it says only
> that the SDK does not hand it a peer verdict or an execution fact the peer never gave. Retry
> policy outside this adapter is not this adapter's proposition.

The closing sentence dropped "beyond what ASM-0042 names": nothing about the transport below
is named any more, because nothing is assumed about it.

## 2. The repair — what the aggregate deadline now is

`_read_bounded` in `sdk/python/python/mcp_re_sdk/mtls.py`. Two mechanisms compose into the
cap, and the worst case is stated rather than rounded off:

1. **`read1`, never `read`.** `HTTPResponse.read(n)` fills to `n`, so one call absorbs an
   unbounded number of underlying reads and the loop's deadline check is not reached while it
   does — which is exactly how a bound written that way came to be advertised and not
   enforced. `read1(n)` returns what ONE underlying read produced, chunked framing included.
   What that buys is precise and no more: the aggregate-deadline check cannot be suppressed
   across multiple underlying reads, so **once the deadline has passed, no NEW underlying
   read is begun.**
2. **The per-recv bound ends the read already in progress.** One underlying read may straddle
   the deadline — a peer that goes silent mid-read is not observable from a check made
   between reads — and `http.client` already carries that bound from `options.timeout`.

So the claimed cap is **the aggregate deadline plus at most one per-recv timeout — at most
`2 * options.timeout`** under the single value a deployment sets. It is deliberately NOT
claimed as an exact wall-clock bound. Both halves are measured (§3), including the silent
peer.

**Why the socket's timeout is NOT narrowed to the time remaining.** That would tighten the
worst case to exactly the deadline, and it was implemented and then withdrawn on measurement:
this transport frames with `Connection: close`, so `http.client` hands the connection to the
response and closes the socket object during `getresponse()`. A socket captured before that
call raises `[Errno 9] Bad file descriptor` on `settimeout`, and the only live handle left is
a private attribute of the response's file object. A bound reaching through a foreign
object's internals is the kind of dependency this SDK registers as a premise — and the whole
point of the ruling was to stop registering premises where local enforcement will do. The
composed bound above needs no premise at all.

Two things NOT done, both named in the ruling: `_READ_CHUNK_BYTES` is unchanged (a smaller
fill size is a smaller window, not a bound), and no fake with short-read semantics remains.
`max_response_bytes` is untouched and independent; `timeout=None` still means no bound on
either axis.

## 3. Proof that the deadline works under production `http.client` semantics

The peer is a real socket. It accepts, consumes the request, sends a valid response head with
a 1 MB `content-length`, then writes one body byte every 10 ms for up to an 8 s budget. The
response is read through a real `http.client.HTTPResponse`. The per-recv (socket) bound is set
to **5 s** while the aggregate bound under test is **0.5 s**, so the socket is never idle long
enough to time out: what ends the read is the aggregate deadline or nothing.

| control | what it establishes |
|---|---|
| `test_the_aggregate_read_deadline_holds_against_a_real_trickling_peer` | the read ends at the deadline (0.4 s ≤ elapsed < 3.0 s), the peer had NOT finished its body, and it was trickling throughout — so the end came from the bound, not from the peer stopping |
| `test_the_full_mtls_path_bounds_a_trickling_peer` | the same over real TLS through the shipped `mtls_poster`, the only path that reaches the reader in production, with the single `timeout` a deployment actually sets |
| `test_a_response_inside_both_bounds_still_reads_whole` | the positive mirror on the same real peer: an ordinary reply is returned whole |
| `test_the_byte_ceiling_still_fails_closed_one_byte_past_it` | the ceiling holds with the clock nowhere near — the two bounds are independent |
| `test_no_timeout_means_no_aggregate_bound_either` | `timeout=None` bounds neither axis |
| `test_a_peer_that_goes_silent_is_ended_by_the_per_recv_bound` | the composed bound's other half: a peer that answers, sends three bytes and then holds the connection open in silence for 30 s is ended in under 2 s — the stated `2 * timeout` worst case — rather than holding the exchange and its concurrency slot |

**Both halves were shown load-bearing by removing them** (measured, then reverted):

| weakening | result |
|---|---|
| delete the deadline check, keep the per-recv timeout | `DID NOT RAISE MtlsTransportError` — both trickle controls RED |
| restore `read(want)` in place of `read1(want)`, keep the deadline check | `the aggregate deadline did not bound the read (8.01s)` — RED at the peer's budget |

The second is the exact defect R9-C010 recorded, and it is now caught by a control rather than
registered as a premise.

## 4. Proof that a timeout does not synthesize execution or retry facts

`test_a_transport_deadline_does_not_synthesize_what_the_peer_never_said`, in the root battery,
drives the pump with a poster raising precisely what `_read_bounded` raises, alongside a second
unrelated exchange. It asserts all five of the ruled points:

1. the affected exchange is failed and delivered, correlated to its own id;
2. the message carries the SDK's local prefix and **no** `mcp-re.*` peer verdict;
3. no `executionStatus` / `not_executed` anywhere in the rendered error;
4. no `retrySafety` / retry-safe verdict;
5. the unrelated exchange is unaffected and the correlation store is left empty.

**Measured negative control:** making `_one`'s local-failure path attach
`{"executionStatus": "not_executed", "retrySafety": "retry_safe"}` takes it RED
(`'not_executed' is contained here`). Reverted.

**The mutation lane cannot hold this as a probe.** `tools/verification/verify-mutations` runs
`cargo test -p <package>` and reads libtest output; it has no Python ecosystem. Registering a
`[[probe]]` naming a `.py` path and pytest node ids would be a probe no lane can execute —
the "configured but enforces nothing" shape this repository refuses. So the weakenings above
are recorded here as measurements, and extending the lane to the Python ecosystem is a
platform change this campaign did not make.

## 9. Python-runtime evidence — the gap, and how it was closed

Batch 6B measured that the evidence was narrower than the support claim. That measurement,
and the work that closed it, in one place.

### What was measured on 2026-09-03 (the gap)

```
supported set:      CPython 3.10–3.14   (requires-python = ">=3.10", unbounded above)
authoritative root: 3.14 only, on whatever interpreter `uv` found on the runner
secondary coverage: 3.12, directory-wide, not the registered battery
unmeasured:         3.10 / 3.11 / 3.13
runtime identity:   pinned nowhere, and not a fingerprint input
```

The last line was the sharp one: `pyproject.toml` and `uv.lock` are fingerprint inputs and
the interpreter was not, so a runner upgraded from 3.14 to 3.15 would have changed the
runtime under every control while the unit fingerprint stayed put and no review went stale.
It sat directly under this claim, because the repaired read bound rests on stdlib `read1`
behaviour, which is a per-minor fact.

### Runtime identity is now part of the evidence

`verification/policy/toolchains.lock.toml`:

```toml
[python]
state = "resolved"
ecosystem = "python"
interpreters = ["3.10.20", "3.11.15", "3.12.13", "3.13.15", "3.14.7"]
```

**Ecosystem-scoped**, and that is a decision rather than a detail. `_toolchain_identity`
filters on `ecosystem`, so this entry enters Python units' fingerprints only: the
interpreter decides the outcome of the Python batteries and of nothing else, and a global
entry would dirty all 76 units including every Rust one. Verified by measurement — a Rust
unit's fingerprint is byte-identical across the change; the Python unit's moved.

**Exact patch versions, not minors.** A minor list would let 3.12.9 and 3.12.20 record the
same identity, which is "resolved by PATH" one level down.

### The registered battery is the authoritative selector, once per runtime

`verify-tests` runs the declared node ids in each pinned interpreter's prepared environment.
Before a single test runs it asks that interpreter its version and refuses an environment
that does not report exactly the pin; a missing environment is a FAIL, never a skip.

`scripts/prepare_python_matrix.sh` prepares the five environments — outside the lane,
because a lane that builds what it measures can report a battery it has just made pass —
from ONE abi3 wheel and the committed lock, so the environments differ in the interpreter
and in nothing else.

```
cpython-3.10.20 pytest: 39 passed
cpython-3.11.15 pytest: 39 passed
cpython-3.12.13 pytest: 39 passed
cpython-3.13.15 pytest: 39 passed
cpython-3.14.7  pytest: 39 passed
```

### The dependency resolution is measured at last

`sdk/python/uv.lock` was `.gitignore`d as a maturin by-product, so `project_inputs` named it
while `_tracked_files` filtered it out: a claimed fingerprint input contributing nothing.
The platform's own control had predicted this exact repair — *"a root over it must either
commit a lockfile or register the looseness as a premise"* — and #746 took the first option.
The lock is tracked, the environments are built from it, and `test_ecosystems` now asserts
its presence where it asserted its absence.

### The support claim may not exceed the evidence

`requires-python = ">=3.10,<3.15"`, and `scripts/python_runtime_gate.py` fails the build in
both directions — a supported minor no pinned interpreter measures, and a pinned interpreter
outside the supported range. Eight `--selftest` cases including the positive one; wired into
`local_gate.sh` AND `ci.yml`, because a control that lives only in the local gate is enforced
by remembering to run it.

### What the matrix found

**One version-specific defect.** `sdk/python/tests/test_transport_e2e.py` imported `tomllib`
at module level, so on 3.10 — a supported minor — the file was a COLLECTION ERROR that took
every other file's result with it in a directory-wide run. It is now declared with the same
`importorskip` mechanism as its other environmental requirements, so 3.10 skips the
live-proxy lane and says why. The shipped package imports no `tomllib`; this was the test's
own dependency.

**No behavioural divergence between minors.** All 39 controls pass on all five interpreters,
including every deadline control on the real trickling and silent peers.

### Independent evidence, preserved

The `downloader — Python maturin wheel` CI job still installs the built wheel into a clean
environment on ubuntu / CPython 3.12.14 and runs the whole tests directory (`219 passed, 1
skipped`). It is deliberately NOT the registered battery — it selects by directory, so it
cannot answer for a control dropped from `verification.toml` — and that is exactly why it is
worth keeping beside one that does.
