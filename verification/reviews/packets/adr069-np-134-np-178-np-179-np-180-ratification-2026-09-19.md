## What landed, and the clause that contains it

THM-0097, statement, verbatim:

> For one replica, and for every Request-slot `(signer, key_id)` its trust plane's resolver is
> asked about:

and

> A verification key the resolver returns is either the answer the replica's CURRENT
> materialized trust snapshot gave on this resolution — always under the live tier, and under
> the bounded-cache and push tiers whenever no serving cache entry exists for the pair

The per-pair quantification is what `compose_key_is_injective_across_delimiter_containing_pairs`
and `push_for_a_different_key_does_not_evict_the_active_entry` measure: without an injective
key "the entry for the pair" does not denote, and a lookup for one pair can be answered from
another's. *Always under the live tier* is `no_positive_caching_consults_inner_every_call`,
which is an R1 into `proxy.trust_resolution_window` — `live_trust.rs` is already that unit's
path and that unit already holds three live-tier controls.

**Not THM-0119, although THM-0119 states the identical shape.** THM-0119's statement carries
*"The composite key the reference resolver indexes by is injective across pairs whose members
contain the delimiter"*, and its scope routes this carrier away in the same breath:

> THE SEAM AND THE REFERENCE IMPLEMENTATION. Nothing here is about the runtime trust plane's
> tiers, its caching windows, or its revocation channel — those are THM-0097 through
> THM-0100's, over `proxy.trust_resolution_window` and `proxy.trust_reload_cadence`.

Two carriers hold the same rule; `core.trust_resolver_seam` owns one and this unit owns the
other. Whether that is one fact represented twice (twelve-questions Q10) is a consolidation
question for the owner and is NOT taken here.

## The four residue propositions

### NP-134 — the cache degrades by ceasing to cache, never by ceasing to answer (4 controls)

`trust_cache::tests::{past_the_ceiling_the_cache_stops_caching_but_keeps_answering,
expired_entries_are_swept_rather_than_merely_ignored, prune_evicts_closed_windows,
not_found_uses_short_ttl_so_a_new_key_propagates}`.

THM-0097 excludes every one of them, in two sentences:

> Not a liveness claim: that an admitted key IS served is not stated. What is cached
> NEGATIVELY — a revoked or unknown pair, and for how long — is an availability fact and is not
> part of this claim, which is about the keys that are served.

*Keeps answering* is a liveness claim by name. *Not-found uses a short TTL* is the negative
cache by name. The sweep and the prune are subtler and are refused on the same ground from the
other side: THM-0097 says *"at or past that deadline the cache serves nothing and the snapshot
is consulted"*, and an expired entry that is IGNORED on read serves exactly nothing too — the
two implementations are indistinguishable in what is served, and differ only in what the map
retains. The sweep's actual consequence is unbounded memory growth, one entry per distinct
keyid an unauthenticated peer presents, because the keyid gate runs before trust resolution.
That is a resource-ceiling fact and no theorem states one.

**Statement.** Past its entry ceiling the cache stops admitting new entries and keeps serving,
so a memory bound never becomes an outage; an expired entry is swept rather than merely
ignored, and `prune` evicts closed windows, so a bounded cache is bounded in fact; and a
not-found answer is cached under a short TTL so a freshly published key propagates within that
TTL rather than within `T`.

**Security consequence.** Two opposite failures, both real. A cache that stopped answering when
it stopped caching is a self-inflicted outage triggered by load. A cache that never sweeps is a
memory exhaustion an unauthenticated peer drives at will. Caching *unknown* for the full `T`
would delay a legitimately new key by the whole window, which is why the negative TTL is short
and why its shortness is a control rather than a constant.

**Scope.** The cache's DEGRADATION behaviour on one replica. Not the positive algebra or the
deadline arithmetic (THM-0097's). Not what the snapshot represents. Not cross-replica
agreement.

**Severity.** `critical`, the registry's own `NP-134.consequence`.

**`depends_on`.** `THM-0097` — the positive algebra is the premise the degradation is defined
against.

### NP-178 — revocation is conjunctive across authorities, and a source outage fails closed (2)

`live_trust::tests::{revocation_source_outage_fails_closed,
second_revocation_authority_rejects_even_when_key_status_active}`.

THM-0097 characterizes what ONE resolver answers under ONE snapshot and ONE cache. It states
nothing about how many revocation authorities are consulted or how their answers combine, and
`proxy.trust_resolution_window` already carries the single-authority outage case as
`live_trust::tests::store_outage_fails_closed_never_active` — so the residue here is precisely
the part that is about a SECOND authority.

**Statement.** A second revocation authority's rejection stands even where the key status is
active — the authorities COMPOSE rather than being alternatives — and an outage of a revocation
source fails closed rather than resolving to "not revoked".

**Security consequence.** A revoked key keeps verifying for as long as the revocation source
stays down, which is exactly when an attacker would want it down. The composition clause is the
repository's standing rule that two mechanisms which COMPOSE must not be modelled as
alternatives: read as alternatives, the weaker authority's silence overrides the stronger one's
rejection.

**Severity.** `critical`, carried from NP-134.

### NP-179 — the window in force is the strictest applicable one, and a long one is flagged (2)

`window_policy::tests::{strictest_applicable_t_picks_the_tightest_window,
t_exceeds_recommended_max_flags_long_windows}`. Carrier
`mcp-re-proxy/src/trust_plane/window_policy.rs`, which is in NO unit's `paths` and is listed in
`config/unit-closure-exclusions.toml`.

THM-0097 takes `T` as an input, in terms: *"The deadline is the cache's clock reading at first
caching plus the declared window `T`"*. How `T` is DERIVED from the applicable rules is a
premise of that arithmetic, not a decomposition of it, and clause 2 of the subsumption test
fails on the quantifier rather than on the subject. `t_exceeds_recommended_max_flags_long_windows`
fails clause 3 as well: an advisory an operator reads is an externally meaningful product
promise.

**Statement.** Where several window rules apply, the one in force is the tightest of them; and a
configured window past the recommended maximum is flagged rather than silently accepted.

**Security consequence.** A deployment matching two rules served under the looser one has a
revocation window longer than the one its stricter rule promised, and the difference is
invisible because both rules are legitimately configured.

**Severity.** `critical`, carried from NP-134.

**Note for the owner.** Ratifying this is also the occasion to give `window_policy.rs` an owner
and shrink `config/unit-closure-exclusions.toml` by one.

### NP-180 — the only window rule production can construct is the identity (1), `structural`

`window_policy::tests::the_only_input_production_can_build_makes_the_rule_the_identity`.

**This row is `structural`, not `tested`, and that is why it is its own record.** It is a
*possession is the proof* statement about which inputs a constructor admits. ADR-MCPRE-068 §4.1
classes that `structural`, whose falsifier is a COMPILE REFUSAL over the illegal construction,
and §9 N4 forbids substituting one probe class for another. Sweeping it into a `tested` unit
beside its two `window_policy` file-mates would have registered it under evidence that cannot
falsify it — a `mutation://` weakening of a runtime branch says nothing about what can be
built. A passing `cargo check` witnesses no seal either: the owner adopting this record owes a
HOSTILE REFUSAL PROBE naming the construction that must not compile.

**Statement.** Over the inputs production can actually build, the window rule is the identity:
no reachable construction produces a rule that moves a window at all.

**Security consequence.** If the rule's other branches are reachable, a window an operator
configured is transformed before it is applied, and the transformation is invisible precisely
because the ordinary path never takes it.

**Severity.** `critical`, carried from NP-134.

## Evidence that already exists

All nine residue controls run and pass in the default lane. **No falsifier exists for any of
them.** N1 is at 0 open estate-wide with the ratchet closed to new work, so each unit the owner
authorizes ships with its own probe in the same change — a `mutation://` one for NP-134,
NP-178 and NP-179, and a `structural://` compile-refusal one for NP-180.

## The fingerprint these would carry

Each new theorem carries `theorem_id`, `theorem_claim`, `theorem_dependencies` and
`theorem_review_requirement`. `_dependency_closure` walks DOWNWARD, so a new theorem naming
`THM-0097` puts THM-0097's claim digest into the NEW closure and puts nothing into THM-0097's.
`supported_by` is not a fingerprint component (`_fingerprint.py:707-727`), so **granting any of
these four moves NO existing theorem's fingerprint.** An existing fingerprint moves only if the
owner also edges an EXISTING theorem down to a new claim: making any of these a premise of
THM-0097 would move THM-0097 and its transitive dependents THM-0099, THM-0100 and the root
THM-0074.

1. Are these four propositions, or fewer? The split was made on twelve-questions Q2 — cache
   degradation, revocation-authority composition, window selection, and constructibility are

4. NP-180 needs a `structural` owner with a compile-refusal probe. Is the illegal construction
