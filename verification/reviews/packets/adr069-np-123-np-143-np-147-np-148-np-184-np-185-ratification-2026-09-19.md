## Residue 1 — NP-121, ten rows: the replay tier's vocabulary and its published guarantee

Carrier `mcp-re-proxy/src/replay_tier.rs`, default lane, `high`.

`parse_round_trips_the_simple_tiers`, `parse_rejects_unknown_and_malformed`,
`parse_wait_quorum_extracts_quorum_and_timeout`, `wire_names_are_the_semantic_adr_names`,
`every_tier_has_a_nonempty_guarantee`, `no_tier_claims_unconditional`,
`tier_claim_ceiling_async_is_not_linearizable`,
`startup_audit_line_carries_backend_tier_and_guarantee_no_nonce`,
`a_tier_promising_wait_supplies_wait_params`,
`wait_quorum_params_carry_the_parsed_quorum_and_timeout`.

**This campaign's own referral packet is corrected here.**
`work/campaigns/mcp-re-adr069-product-claim-closure/packets/NP-121-residue.md` states that
seven of these are R2 under THM-0086 and are *"ordinary registration work, not an owner
question"*. They are not. THM-0086's scope opens *"CONFIGURATION PROJECTION ONLY"*, and its
statement is about which tier `MaterializedReplay::materialize` hands the serving path. The
clause the packet matched on — *"a backend this build does not carry is refused by name rather
than substituted"* — is about a BACKEND the build lacks, and is already measured by
`replay_plane::materialized::tests::a_backend_the_build_lacks_is_refused_and_named` inside
`proxy.replay_materialization`. It is not about `ReplayDurabilityTier::parse("cluster")`.

The operational test settles it in one line: **rename every wire name and empty every
guarantee string, and THM-0086 still holds** — the tier the plan selected is still the tier
handed over. A claim you can break without breaking the theorem is not a decomposition of it.

THM-0118 cannot take them from the other side. Its scope is *"THE SEAM, NOT A DEPLOYMENT'S
TIER"* and *"nothing here establishes that any deployed cache is shared, durable, or
linearizable"*, and its owner `core.replay_seam` is in `mcp-re-core`, so no unit under it can
name a `mcp-re-proxy` path.

**The proposition, as it would be stated.** Two, and the owner should expect to say which:

> **(a) The vocabulary.** The tier an operator names on the command line is parsed into
> exactly the tier that name means, or refused; the wire names are the ADR's names; and a
> name that is not one of them is never resolved to a neighbouring tier.
>
> **(b) The published guarantee.** What a deployment publishes about its replay tier is what
> the deployment has: every tier carries a non-empty guarantee, no tier's guarantee is
> unconditional, the async tier's ceiling is its own bounded-window claim and never the
> linearizable one, a tier promising a wait supplies the parameters that wait is made of, and
> the startup audit line carries the backend, the tier and the guarantee and no nonce.

**NP-063 is the same question for the other vocabulary** — the revocation tier, nine controls,
still unregistered — and the two should be answered together or the estate will hold one
answer for two identical shapes.

## Residue 2 — NP-123, one row: what an OFF line tells the operator to do

Carrier `mcp-re-proxy/src/serving_capabilities.rs`, default lane, `high`.
`tests::every_off_line_tells_the_operator_what_to_do_about_it`.

The other five rows landed: THM-0077's statement contains them, and the falsifier M336 turns
an unopenable retention directory into an OFF posture line and drives
`an_unopenable_retention_directory_refuses_startup_naming_the_flag` red while the other four
stay green.

This row does not follow them, and the reason is a quantifier rather than a subject. The
deployment's posture is IDENTICAL whether or not the OFF sentence names a flag; what changes
is what an operator can do next. That is the operator-facing claim surface — the same axis as
NP-132 (each refusal token names its own authority) and NP-145 (the two vocabularies agree
field for field), both of which this campaign referred rather than registered.

> **The proposition.** Every OFF posture line names the flag that turns the capability on, or
> the build feature whose absence means nothing can, and says that the capability is off.

## Residue 3 — NP-143, four rows: a carrier no deployment reaches

Carrier `mcp-re-proxy/src/capability_materialization/ingress.rs`, default lane, `critical`.
`the_mode_c_verifier_is_built_only_for_the_attested_ingress_binding`,
`a_mode_c_verifier_missing_its_audience_fails_closed_rather_than_defaulting`,
`a_mode_c_verifier_rejects_an_unusable_attestor_key_rather_than_dropping_it`,
`the_retained_mode_c_verifier_still_admits_an_assertion_from_its_configured_attestor`.

The scheduling analysis routed these to THM-0077 as materialization refusals, and they read
exactly like the five NP-123 rows that landed there. **They are refused on a fact about the
tree, not on a reading of the text.** `config_state::transport::undeployable_transport_binding_refusal`
returns a refusal for every `PeerIdentityEvidenceRequest::AttestedIngress`, unconditionally,
with no `cfg` and no configuration that turns it off. The module's own documentation states
the consequence: *"Retained, not live. No validated deployment reaches it."*

THM-0077 quantifies over *"Every security capability held by the serving runtime"*. A
capability no validated deployment can hold is not one of them, and attaching these rows would
make a declared root's evidence range over code the serving runtime never executes.

**This is the question NP-146's residue already asks** — *does dormant code get a claim at
all?* — over `async_replay/l1_fast_reject.rs`. Two carriers, one question, and it should be
answered once. THM-0105's scope shows the estate's current practice: it EXCLUDES the dormant
store from the owning unit's paths by name.

> **The proposition, if the owner rules that dormant capabilities are claimable.** A retained
> verifier is built only for the binding it belongs to, is built with every fact its
> configuration named or not at all — no defaulted audience, no silently dropped attestor key
> — and still admits a genuine assertion from its configured attestor, so the capability stays
> correct rather than merely compiling.

## Residue 4 — NP-147, two rows: the automatic topology, and a control that cannot fail

Carrier `mcp-re-proxy/src/async_fleet/mod.rs`, default lane, `high`.
`auto_is_always_at_least_one_shard_of_one_worker`, `auto_keeps_a_shard_per_cpu_and_adds_depth`.

Refused for two independent reasons, and either alone is sufficient.

**The axis.** What the automatic path computes is throughput and availability policy — a shard
per cpu because shards own the `SO_REUSEPORT` listeners that parallelise `accept`, depth on top
because a readied task needs a thread. The test's own comments quote rps measurements. THM-0077's
scope excludes it in its first line: *"SECURITY POSTURE, not liveness and not permanent runtime
availability."*

**The measurement.** Both rows assert over `auto_for`, a helper defined INSIDE `topology_tests`
as `(cpus, DEFAULT_MAX_WORKERS_PER_SHARD.min(cpus).max(1))`. It restates the policy rather than
calling `resolve_topology`, so **no edit to production code turns either control red.** A
control that cannot be falsified by a production change is not evidence for any theorem. That
is a finding about the controls, not about the theorem, and it is the owner's to act on: either
the two are rewritten against `resolve_topology` — at which point the axis question is still
open — or they are `not-evidence`.

> **The proposition, if the owner rules the automatic path claimable AND the controls are
> repointed at production.** A deployment that stated no topology is never given a degenerate
> one: at least one shard of one worker on any host, one listener per cpu, and depth added on
> top rather than traded against shards.

## Residue 5 — NP-148, one row: exactly one rotation worker

Carrier `mcp-re-proxy/src/signing_plane/mod.rs`, default lane, `critical`.
`rotation_owner_tests::materialize_publishes_a_usable_key_and_owns_one_rotation_worker`.

**The NP-124 question, answered.** The work package asks whether this record's *owns ONE
rotation worker* clause is the same lifetime family as NP-124 and should leave the slice with
it. The answer is *neighbour, not member*, and the tree decides it:

* NP-124's proposition is the shared control-plane RUNTIME in `control_runtime.rs` — *"a
  deployment that needs no control-plane client starts NO runtime"*, *"dropping the owner stops
  work a surviving handle had started"*. That is the OUTLIVING question.
* The signing plane's outliving question is **not open**.
  `handle_lifetime_tests::a_surviving_signer_does_not_keep_the_rotation_worker_alive`,
  `::a_signer_that_outlives_the_plane_stops_signing` and
  `::a_mint_completing_inside_the_drop_join_window_cannot_restore_signing` are already
  registered under THM-0062 inside `proxy.delegated_signing_credential`.
* What is left is a COUNT at materialization — `plane.worker_count() == 1` — which is
  ADR-MCPRE-056 §9's worker-ownership rule and is stated by no theorem.

So NP-148 stays as one row, and an owner settling NP-124 should settle it in the same sitting:
both are worker- and runtime-ownership propositions with no claim above them.

**Why the whole control could not simply be registered under THM-0062.** Its two assertions are
one symbol. THM-0062 contains the first — a usable key published, whose twin
`delegated_wiring::tests::builds_and_first_rotate_publishes_a_snapshot` is already in that
unit's battery — and not the second. Registering the symbol would put a worker-count
proposition inside a battery whose theorem never states it, which ADR-MCPRE-069 §5 holds
strictly worse than leaving it unregistered.

> **The proposition.** A materialized plane owns exactly the workers its own materialization
> started — one rotation worker, not zero and not two — so no key-minting thread exists that
> the plane's drop does not reclaim.

## Residue 6 — NP-184, two rows: the PIN file's mode and its content

Carrier `mcp-re-proxy/src/capability_materialization/key_source/pin.rs`, default lane,
`critical` (carried from NP-143). `a_group_readable_pin_file_is_refused`,
`the_pin_file_reader_trims_a_trailing_newline_and_refuses_an_empty_file`.

Split out of NP-143 under RR-002 C5: a PIN file's permission bits and a Mode-C verifier's
construction are two describable propositions over two carriers, and C5 forbids filing them as
one record.

No theorem states the file MODE a credential on disk must have. THM-0077 is the nearest and
does not reach it: its subject is the deployment posture an OWNER SELECTED, and a file's group
bit is a fact about the host that no configuration declares. Nothing in the statement, the
consequence or the scope quantifies over what the filesystem says.

> **The proposition.** A credential read from a file is refused unless the file is readable by
> its owner alone, and the value read is the file's content without its line terminator — an
> empty file being the absence of a credential rather than an empty one.

## Residue 7 — NP-185, one row: redaction at the consumer

Carrier `mcp-re-proxy/src/capability_materialization/key_source/pin.rs`, default lane,
`critical` (carried from NP-143). `a_secret_string_does_not_print_its_value_or_length`.

**The reattribution that looks obvious is refused twice over, and the second refusal is the
one that matters.** `proxy.operator_facing_redaction` states exactly this proposition —
*"possession of the rendered form IS the statement that the secret is already gone"* — so an R1
looks free.

1. It is not reachable. That unit's `paths` are `deployment_request/secret_string.rs` and
   `deployment_request/inner_backend_display.rs`; this control's source is
   `capability_materialization/key_source/pin.rs`, and a unit's `paths` may not be widened to
   reach a control. **The unit's own closure note already refuses it by name**: *"`capability_materialization::key_source::pin`
   asserts the same property at the CONSUMER and is deliberately NOT named: its source is not
   in this unit's `paths`, so citing it would be the SF-1 defect … The closure gate refuses it,
   which is the gate working."*
2. It would close nothing if it were reachable. `proxy.operator_facing_redaction` is itself one
   of the **twenty units no theorem supports**. An R1 into a theorem-less unit is a re-filing,
   not a discharge, and presenting it as one would make the graph look one control closer to
   root completeness than it is.

No theorem in the estate claims redaction. That is the gap, and it is the same gap on both
sides of the seam.

> **The proposition.** A value classed as a secret discloses neither its content nor its length
> wherever it is rendered — at the form that carries it and at the consumer that spends it —
> because a length is a search space.

## Fingerprints

Granting any of these packets moves **no existing theorem's fingerprint**.
`fingerprint_theorem` has five components — `encoding_version`, `theorem_id`, `theorem_claim`,
`theorem_dependencies` and `theorem_review_requirement` — and `supported_by` is not one of
them. `_dependency_closure` walks downward, so a new theorem `depends_on` an existing one puts
the existing claim digest into the NEW theorem's closure and nothing into the existing one's.
An existing fingerprint moves only if the owner also adds an edge from an existing theorem down
to a new claim, or edits an existing claim's text.
